# 彩票预测项目的科学实现方案

> 角色：高级数据工程师 / 机器学习工程师
> 版本：v1.0　日期：2026-09-11
> 定位：数据采集 → 统计检验 → 特征工程 → 建模回测 → 全栈展示 的完整工程闭环

---

## 1. 项目背景

彩票开奖数据（双色球、大乐透、福彩3D等）是少数长期公开、格式规整、更新频率稳定的真实世界时间序列数据：官方每期发布开奖号码、销售额、奖池金额和中奖注数，历史数据可追溯 20 年以上，样本量在 3000 期以上，非常适合作为数据工程与统计建模的练手数据集。

同时，"彩票预测"是大众搜索热度极高的话题，市面上充斥着大量伪科学预测工具（收费荐号、"AI必中"软件等）。这些工具无一例外利用赌徒谬误和幸存者偏差误导用户，且多数涉嫌违规。

本项目以工程技术手段切入这个高热度题材：不承诺预测，而是用真实数据、严格的统计检验和可复现的回测，科学地验证"彩票能否被预测"这一问题，并把验证过程做成一个可交互的数据产品。

## 2. 项目真实目标

| 层级 | 目标 | 验收标准 |
|---|---|---|
| 工程目标 | 建成自动化数据采集、清洗、存储、建模、回测、展示的完整 Pipeline | 每日定时增量更新，端到端无需人工干预 |
| 统计目标 | 对开奖数据做系统性随机性检验，输出可复现的统计报告 | 每个检验给出统计量、p 值和置信区间 |
| 建模目标 | 实现并回测 5+ 类模型，用假设检验证明其命中率与随机基线无显著差异 | 回测框架可复现，结论附 p 值 |
| 产品目标 | 输出一个带免责声明的数据分析平台 + 娱乐性质号码生成器 | Web 可访问，核心接口 P95 延迟 < 300ms |
| 简历目标 | 展示数据工程、统计推断、ML 工程化、全栈开发四项能力 | 文档 + 代码 + 可运行 Demo 齐全 |

明确排除的目标：不以任何形式承诺或暗示能提高中奖概率，不提供收费荐号服务。

## 3. 彩票预测是否可行的统计学解释

### 3.1 理论分析

双色球一等奖的组合数为 C(33,6) × 16 = 1,107,568 × 16 = **17,721,088**，单注命中概率约 5.64×10⁻⁸。开奖过程为物理摇奖，各期之间相互独立，球号在理想条件下服从均匀分布。因此：

- **独立同分布假设**：第 N+1 期结果不依赖第 1..N 期结果，历史数据中不存在可被学习的条件分布 P(下一期 | 历史)。
- **大数定律**：长期频率收敛于理论概率，但收敛不提供任何单期预测信息。
- **赌徒谬误**："某号码很久没出所以该出了"是条件概率的误用；独立试验下 P(出现 | 连续遗漏 k 期) = P(出现)，遗漏不改变下一期概率。
- **信息论视角**：若开奖真随机，单期结果的熵为 log2(17,721,088) ≈ 24.08 bit，任何模型的条件熵不低于此值，即互信息 I(历史; 未来) = 0。

### 3.2 需要实证排除的例外

理论上"摇奖机不完美"（机械磨损、球重差异）可能引入微弱偏差。项目的统计检验章节正是用数据验证这一点：对真实开奖序列做卡方均匀性检验、游程检验、序列相关检验。若所有检验均无法拒绝"均匀独立"原假设，则从实证上证明预测不可行；若某个检验显著拒绝，则发现了一个真实的统计异常，这本身也是有价值的研究结论。

### 3.3 结论

预测中奖号码不可行，这不是项目的中止理由，而是项目要**用工程方法证明的核心命题**。模型章节的存在价值是方法论对比：展示不同复杂度的模型在真正的无信号数据上都会收敛到随机基线，以此证伪市面上的预测骗局。

## 4. 可落地项目定位

项目名称：**LotteryLab —— 彩票开奖数据分析与随机性验证平台**。

核心功能四件套：

1. **数据中台**：官方开奖数据的定时采集、清洗、入库（支持双色球、大乐透两种玩法）。
2. **统计实验室**：随机性检验报告（均匀性、独立性、熵分析），每期数据更新后自动重算。
3. **回测实验室**：用户可选模型、选历史区间，在线运行模拟投注回测，输出资金曲线和显著性检验结果。
4. **号码生成器**：明确标注"娱乐用途、与中奖概率无关"的号码推荐工具，内置多种生成策略（纯随机、频率加权、冷热均衡），作为流量入口。

非目标：不做付费预测、不做"必中"营销、不抓取需要登录或明确禁止爬取的数据源。

## 5. 数据来源与字段设计

### 5.1 数据来源

| 来源 | 内容 | 方式 | 更新频率 |
|---|---|---|---|
| 中国福彩官网 (www.cwl.gov.cn) | 双色球开奖公告 | HTTP 公开接口，遵守 robots.txt，间隔 ≥ 10s | 每周二/四/日 21:15 后 |
| 中国体彩网 (www.lottery.gov.cn) | 大乐透开奖公告 | 页面解析 + 字段映射 | 每周一/三/六 21:25 后 |
| 本地兜底 CSV | 历史全量数据 | 一次性导入 | 手动 |

采集策略：先请求官方 JSON 接口，失败降级到页面解析，再失败重试 3 次（指数退避）并告警。所有原始响应落盘 `raw/` 目录保留 90 天，保证可回溯。

### 5.2 表结构（PostgreSQL）

```sql
CREATE TABLE lottery_draw (
    id           BIGSERIAL PRIMARY KEY,
    game         VARCHAR(16)  NOT NULL,          -- 'ssq' 双色球 | 'dlt' 大乐透
    issue        VARCHAR(16)  NOT NULL,          -- 期号，如 '2026105'
    draw_date    DATE         NOT NULL,          -- 开奖日期
    red_balls    SMALLINT[]   NOT NULL,          -- 红球/前区，升序存储
    blue_balls   SMALLINT[]   NOT NULL,          -- 蓝球/后区
    sales_amount NUMERIC(14,2),                  -- 当期销售额（元）
    pool_amount  NUMERIC(14,2),                  -- 滚存奖池（元）
    first_prize_cnt  INTEGER,                    -- 一等奖注数
    first_prize_amt  NUMERIC(14,2),              -- 一等奖单注奖金
    source_url   TEXT,
    raw_hash     CHAR(64)     NOT NULL,          -- 原始响应 SHA-256，幂等去重
    created_at   TIMESTAMPTZ  DEFAULT now(),
    UNIQUE (game, issue)
);

CREATE INDEX idx_draw_game_date ON lottery_draw (game, draw_date DESC);
```

派生宽表 `draw_feature` 由 dbt/SQL 定时任务生成，一节一个物化视图，供分析和建模直接读取（字段见第 7 节）。

## 6. 数据清洗规则

按执行顺序定义，每条规则附失败处置：

| # | 规则 | 校验逻辑 | 失败处置 |
|---|---|---|---|
| 1 | 幂等去重 | `(game, issue)` 冲突则跳过；`raw_hash` 相同则跳过 | 记 INFO 日志 |
| 2 | 范围校验 | 双色球红球 ∈ [1,33]，蓝球 ∈ [1,16]；大乐透前区 ∈ [1,35]，后区 ∈ [1,12] | 整条拒绝，写 `dead_letter` 表 |
| 3 | 数量与唯一性 | 红球 6 个（大乐透前区 5 个）且互不重复 | 整条拒绝 + 告警 |
| 4 | 排序归一 | 红球升序存储，消除采集端格式差异 | 自动修正 |
| 5 | 期号连续性 | 同玩法期号应连续递增；出现断号时与官网公告交叉核对 | 标记 `gap_flag=true`，人工确认 |
| 6 | 金额字段 | 销售额/奖池 ≥ 0；缺失时置 NULL 而非 0 | 保留记录，字段置空 |
| 7 | 日期一致性 | `draw_date` 与官方公告日期一致；双色球开奖日必须是周二/四/日 | 不一致则拒绝 + 告警 |
| 8 | 编码与时区 | 统一 UTF-8，时间统一 Asia/Shanghai | 入库前转换 |

清洗结果写入审计表 `clean_audit`（规则编号、影响行数、时间戳），每周自动生成数据质量摘要。

## 7. 特征工程清单

前提声明：以下特征不期望产生预测能力，用途是（a）驱动可视化，（b）作为模型输入以实证"无信号可学"，（c）展示特征工程方法论。所有特征仅用 t 期及之前的数据计算，防止前视偏差。

| 类别 | 特征 | 计算口径 |
|---|---|---|
| 频率类 | `freq_{ball}_w{30,100,all}` | 各号码在滑动窗口出现次数 / 窗口期数 |
| 遗漏类 | `omission_{ball}` | 号码距上次出现的间隔期数；`max_omission_{ball}` 历史最大遗漏 |
| 和值跨度 | `red_sum`、`red_span` | 红球和；最大减最小号 |
| 结构类 | `odd_ratio`、`big_ratio`、`zone_dist` | 奇偶比、大小比（≥17 为大）、三区分布（1-11/12-22/23-33） |
| 形态类 | `consecutive_cnt`、`repeat_cnt`、`same_tail_cnt` | 连号个数、与上期重号个数、同尾号对数 |
| 离散度 | `ac_value` | 算术复杂性：不同差值个数 − (n−1) |
| 时序滞后 | `lag{1,2,3}_red_sum` 等 | 核心统计量的 1~3 期滞后值 |
| 目标编码 | 每号码 one-hot（33+16 维） | 作为序列模型的标签格式 |

特征产出：单期约 120 维，全部入库 `draw_feature` 表，版本字段 `feature_version` 便于迭代。

## 8. 模型方案对比

| 模型 | 原理 | 实现成本 | 预期表现 | 在项目中角色 |
|---|---|---|---|---|
| 随机基线 | 均匀随机选号 | 极低 | 理论概率 | 基准线，所有模型与之对比 |
| 频率加权 | 按历史频率（或反频率）加权采样 | 低 | 无差异 | 展示"热号/冷号"策略无效 |
| 马尔可夫链 | 号码间转移概率矩阵 | 低 | 无差异 | 验证独立性假设 |
| XGBoost 多分类 | 每个号码一个二分类器（出/不出） | 中 | 无差异 | 展示表格特征上树模型无信号 |
| LSTM/GRU | 号码 one-hot 序列建模 | 中 | 无差异 | 展示时序模型在无信号序列上的表现 |
| Transformer | 自注意力序列建模 | 高 | 无差异 | 展示"更大模型也学不到不存在的规律" |

结论模板（回测后填入）：所有模型的命中率均落在随机基线的 95% 置信区间内，二项检验 p 值 > 0.05，无法拒绝"模型等同随机"的原假设。深度学习模型训练损失下降而验证集命中率不升，是典型过拟合，可作为教学案例展示学习曲线诊断。

## 9. 回测框架

### 9.1 设计原则

- **Walk-forward 切分**：以第 T 期为界，训练集 = [1, T−K]，验证期 = T，逐期滚动，严禁任何未来信息泄漏（特征已在第 7 节约束）。
- **模拟投注**：每期模型输出 5 注推荐，按官方奖金规则结算，对比模型组与随机组（同注数）。
- **可复现**：全局随机种子入配置，回测结果存 `backtest_run` 表（参数 JSON + 结果 JSON）。

### 9.2 核心流程（伪代码）

```python
for t in range(train_window, n_issues):
    train = draws[t - window : t]          # 严格历史窗口
    model.fit(train.features, train.labels)
    picks = model.recommend(n_bets=5)      # 当期推荐
    payout = settle(picks, draws[t])       # 按官方奖级表结算
    ledger.append(payout - 5 * BET_COST)

p_value = binom_test(model_hits, total_bets, p=BASELINE_HIT_RATE)
```

### 9.3 输出物

每次回测产出：资金曲线序列、命中率向量、按奖级的收益明细、与随机基线的配对检验结果（p 值、效应量）、参数快照。

## 10. 评估指标

| 指标 | 定义 | 判定口径 |
|---|---|---|
| 命中率对比 | 各奖级命中次数 / 总注数 vs 理论概率 | 落在理论 95% CI 内 → 无信号 |
| 二项检验 p 值 | H0: 模型命中率 = 随机命中率 | p > 0.05 → 无法拒绝，结论为"无预测力" |
| ROI | (总奖金 − 总投入) / 总投入 | 长期期望约 −50%（返奖率决定），两组应无显著差异 |
| 最大回撤 | 资金曲线峰谷最大落差 | 风险刻画，非收益指标 |
| 校准度 | 预测概率 vs 实际频率分箱对比 | 校准曲线贴对角线说明模型至少"知道自己不知道" |
| 卡方统计量 | 各号码实际频次 vs 均匀期望 | 用于开奖机随机性检验 |

项目级成功标准：平台稳定运行 + 所有检验/回测结果可复现 + 报告结论明确（"未发现可利用的预测信号，置信度 95%"）。

## 12. 后端/API 设计

技术栈：Python 3.11 + FastAPI + PostgreSQL 15 + APScheduler（采集调度）+ Redis（接口缓存，TTL 5 分钟）。全部接口只读，无用户资金操作。

| 方法 | 路径 | 说明 | 关键参数 |
|---|---|---|---|
| GET | `/api/v1/draws` | 开奖记录分页查询 | `game, issue_from, issue_to, page, size` |
| GET | `/api/v1/stats/frequency` | 号码频率统计 | `game, window` |
| GET | `/api/v1/stats/randomness` | 随机性检验结果 | `game` |
| POST | `/api/v1/backtest` | 提交回测任务（异步，返回 task_id） | `game, model, issue_range, n_bets, seed` |
| GET | `/api/v1/backtest/{task_id}` | 查询回测状态与结果 | — |
| GET | `/api/v1/recommend` | 娱乐号码生成 | `game, strategy, count` |

响应约定（示例）：

```json
{
  "code": 0,
  "data": { "game": "ssq", "issue": "2026105", "red_balls": [3,8,15,22,27,31], "blue_balls": [12] },
  "disclaimer": "数据仅供统计分析，不构成任何投注建议"
}
```

工程约束：所有响应体强制携带 `disclaimer` 字段；`/backtest` 走 Celery/RQ 异步队列，长任务不阻塞 Web Worker；采集任务与 API 进程分离部署。

## 14. 风险与合规说明

1. **法律红线**：依据《彩票管理条例》，彩票发行与销售属特许业务。本项目不出售彩票、不收取任何与预测相关的费用、不接受投注，仅做公开数据的统计分析，属合法的技术研究范畴。
2. **表述合规**：全站禁止出现"预测""必中""稳赚"等词，统一使用"随机生成""历史统计"。所有输出强制附免责声明。
3. **数据合规**：仅采集官方公开发布页面，遵守 robots.txt，请求频率 ≤ 6 次/分钟，携带真实 UA；不绕过任何反爬或鉴权机制；数据不转售。
4. **技术风险**：官网改版导致采集失败 → 解析器失败告警 + 多源兜底；历史数据纠错 → 以官方公告为准并提供手工修正入口。
5. **伦理风险**：号码生成器可能被误用为"荐号工具" → 生成结果旁固定展示概率说明与防沉迷提示，不提供任何"准确率"暗示。
